# Using the Independent FVM Solver

This guide walks through a complete lid-driven cavity run: define the case,
validate it, solve it, inspect the output files, plot the fields, and compare
the centerline velocities with the Re=100 Ghia reference.

The same JSON handoff can be generated by a CFD setup application. The setup
application does not need to import solver code: it writes the versioned case
document, invokes the backend, then reads the returned summary and artifacts.

## 1. Supported Problem Scope

Case schema version `1.0` currently supports:

- 2D incompressible, laminar, transient flow of a constant-property Newtonian
  fluid.
- A rectangular domain with a uniform Cartesian mesh.
- Uniform initial `u`, `v`, and pressure values.
- No-slip and tangential moving-wall velocity boundaries.
- Homogeneous Neumann pressure-correction boundaries.
- The M3-M6 transient projection solver and M7 post-processing tools.

This is deliberately narrower than a general CFD setup system. Inlets/outlets,
compressible or turbulent models, spatially varying materials, nonuniform or
unstructured meshes, and additional boundary types are rejected by schema
version 1.0. Extend the schema and adapter with tests before sending those
features from a setup application.

## 2. Install and Run the Complete Example

From the project root, install the package and its test tools:

```powershell
python -m pip install -e ".[test]"
```

Run the dedicated user workflow:

```powershell
python examples/run_user_case.py
```

The default case is
[`cases/lid_driven_cavity_re100_workflow.json`](../cases/lid_driven_cavity_re100_workflow.json).
It uses a 16 by 16 mesh and enough time steps to reach the configured steady
state criteria. The current reference run converges in approximately 1,100
steps. It reports its actual convergence state; it does not treat reaching the
step cap as success.

To run another schema-v1 case and choose an output directory:

```powershell
python examples/run_user_case.py --case path/to/setup-export.json --output results/my_case
```

The command has two visualization modes. The default `save` mode writes the
geometry and final-result PNGs without opening windows. `live` mode opens the
geometry window before the solve, updates speed/pressure/convergence windows
after every time step, and still saves the same PNGs and data files. Select it
with an interactive Matplotlib backend:

```powershell
python examples/run_user_case.py --mode save
python examples/run_user_case.py --mode live
```

The live windows stay open at the final state until closed. `--live` remains a
short alias for `--mode live`. Headless systems should use `save` mode; it
preserves the geometry, final-field, centerline, and convergence PNGs without
requiring a display server.

The command returns exit code `0` for a converged simulation and `2` if the
case reached its maximum step count without converging. In either case, it
writes available fields and diagnostics so a capped run can be inspected.

## 3. Define the Problem

The complete JSON structure is in the example case linked above. Its main
sections are:

| Section | Purpose |
| --- | --- |
| `schema_version`, `case_id` | Contract version and stable setup identifier |
| `units` | Unit system; version 1.0 requires SI |
| `physics` | Incompressible laminar transient model |
| `domain`, `mesh` | Rectangle dimensions and uniform cell counts |
| `material` | Density and dynamic viscosity |
| `initial_conditions` | Uniform initial velocity and pressure |
| `boundary_conditions` | One supported velocity-wall type per side and pressure-correction condition |
| `solver` | Time-step cap, CFL limit, step limit, and convergence tolerances |

For example, the Re=100 case uses the following key values:

```json
{
  "domain": {"type": "rectangle", "width_m": 1.0, "height_m": 1.0},
  "mesh": {"type": "uniform_cartesian", "nx": 16, "ny": 16},
  "material": {
    "type": "newtonian_fluid",
    "density_kg_m3": 1.0,
    "dynamic_viscosity_pa_s": 0.01
  },
  "initial_conditions": {"u_m_s": 0.0, "v_m_s": 0.0, "pressure_pa": 0.0},
  "boundary_conditions": {
    "west": {"type": "no_slip_wall"},
    "east": {"type": "no_slip_wall"},
    "south": {"type": "no_slip_wall"},
    "north": {"type": "moving_wall", "velocity_m_s": [1.0, 0.0]},
    "pressure_correction": "homogeneous_neumann"
  }
}
```

The JSON Schema requires all top-level sections and solver controls; the
snippet above shows only the physical setup fields. Copy the full example case
when creating a new case and update the mesh, material, wall data, and solver
settings together. For the square cavity,

`Re = density * lid_speed * cavity_width / dynamic_viscosity`.

Thus `rho=1 kg/m^3`, `U=1 m/s`, `L=1 m`, and `mu=0.01 Pa.s` give Re=100.
The solver does not infer a benchmark Reynolds number from a case ID; it uses
the physical values in the document.

## 4. Validate and Run From Python

A setup application can validate its generated mapping before launching the
backend. Schema errors identify the offending JSON path, and unsupported
features are rejected before numerical work begins.

```python
import json
from pathlib import Path

from fvm import PythonFVMBackend, validate_case_document

case_path = Path("cases/lid_driven_cavity_re100_workflow.json")
case_document = json.loads(case_path.read_text(encoding="utf-8"))
validate_case_document(case_document)

run = PythonFVMBackend().run(
    case_document,
    output_directory=Path("results/lid_driven_cavity_re100"),
)
print(run.summary["status"])
print(run.summary["steps"], run.summary["final_time_s"])
```

The file-based variant performs loading and validation for you:

```python
from fvm import PythonFVMBackend

run = PythonFVMBackend().run_file(
    "cases/lid_driven_cavity_re100_workflow.json",
    output_directory="results/lid_driven_cavity_re100",
)
```

`run.simulation` contains the solver-native fields and time history. `run.summary`
is a JSON-compatible integration result intended for setup software. The
backend is independent of the calling application's classes and APIs.

Applications that need custom per-step visualization can use the observer
instead of the CLI's plotting helper. It is called once after each full
predictor/pressure/projection step and receives read-only-by-contract defensive
copies, so observer code cannot change the run state:

```python
def show_step(diagnostics, velocity, pressure):
   print(
      diagnostics.step,
      diagnostics.time,
      diagnostics.max_divergence_after,
   )

run = PythonFVMBackend().run_file(
   "cases/lid_driven_cavity_re100_workflow.json",
   step_observer=show_step,
)
```

## 5. Check Convergence Before Trusting a Result

The steady cavity solution is obtained by advancing the transient equations
until the configured tolerances are met. Inspect the result status and final
history entry before treating a run as complete:

```python
last_step = run.simulation.history[-1]
print("converged:", run.simulation.converged)
print("termination:", run.simulation.termination_reason)
print("max divergence:", last_step.max_divergence_after)
print("global mass imbalance:", last_step.global_mass_imbalance)
print("velocity change:", last_step.velocity_change)
```

The case controls `max_time_step_s`, `cfl_limit`, and `max_steps` affect run
length and stability. The solver automatically reduces the time step to honor
the explicit-convection CFL limit. If `termination_reason` is
`maximum_steps_reached`, the fields are a transient result, not a steady
solution. Increase the step budget or adjust the time-step cap, rerun, and
check convergence again.

## 6. Read the Output Artifacts

The output directory contains:

| File | Contents |
| --- | --- |
| `case.json` | Canonical validated case document consumed by the backend |
| `summary.json` | Case ID, schema/backend versions, status, Reynolds number, extrema, and final conservation/residual metrics |
| `fields.npz` | Coordinates, pressure, face-centered `u`/`v`, and cell-centered `u`/`v` arrays |
| `metadata.json` | Mesh, solver settings, convergence state, final time, and extrema |
| `history.csv` | Per-step time, CFL, velocity change, continuity, mass imbalance, and linear residuals |
| `ghia_re100.json` | Interior-point Ghia profile values, RMS errors, and benchmark eligibility |
| `geometry.png` | Domain outline, uniform mesh, and moving-wall direction |
| `cavity_fields.png` | Final velocity magnitude, pressure, and streamlines |
| `ghia_profiles.png` | Computed centerline profiles against Ghia reference points |
| `convergence_history.png` | Velocity change, divergence, and pressure residual over time |

Open the compressed field arrays with NumPy:

```python
import numpy as np

with np.load("results/lid_driven_cavity_re100/fields.npz") as fields:
    pressure = fields["pressure"]
    u_faces = fields["u_faces"]
    v_faces = fields["v_faces"]
    u_cells = fields["u_cell_centers"]
    v_cells = fields["v_cell_centers"]
```

Pressure is cell-centered with shape `(ny, nx)`. Face velocities have shapes
`u=(ny, nx+1)` and `v=(ny+1, nx)`. Cell-centered velocity arrays in the export
are interpolated for plotting and do not replace the staggered solution fields.

## 7. Interpret the Ghia Comparison and Visuals

The workflow interpolates the staggered velocities onto `x=0.5` and `y=0.5`,
then computes RMS errors at Ghia's interior Re=100 sample coordinates. Wall
endpoints are excluded, including the discontinuous moving-lid corners. The
reference data source and DOI are documented in
[`src/fvm/postprocessing.py`](../src/fvm/postprocessing.py).

`ghia_re100.json` includes `benchmark_valid`. It is true only when the
simulation reports convergence and the run matches the square Re=100 benchmark
assumptions. A short, capped run can still produce plots and RMS values for
diagnosis, but those numbers are not a benchmark pass. The 16 by 16 example is
for learning the workflow; use the optional grid-study API and compare
successively refined, converged runs before making grid-independence claims.

The live plot updates on every solver step when `--live` is enabled. Saved PNGs
show the starting geometry and final state. The PNGs can also be regenerated/customized through
`plot_cavity_fields`, `plot_ghia_comparison`, and
`plot_convergence_history` in `fvm.postprocessing`.

## 8. Adapt This Workflow

For another problem supported by schema version 1.0:

1. Copy the case JSON and assign a unique `case_id`.
2. Set rectangle dimensions, uniform mesh counts, fluid properties, and
   initial fields in SI units.
3. Assign one supported wall condition to each side. Moving-wall velocity
   must be tangential to its side.
4. Choose a time-step cap, CFL limit, maximum steps, and tolerances appropriate
   to the case.
5. Validate the document, run it through `PythonFVMBackend`, and inspect the
   convergence status before comparing results.
6. Use the exported fields and diagnostics or add problem-specific post-
   processing around `run.simulation`.

For capabilities outside that list, extend the versioned schema and adapter
with focused tests and documentation rather than encoding extra meanings in
existing fields. This keeps the setup-software interface explicit and lets
both projects evolve independently.
