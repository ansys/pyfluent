# Using the Independent FVM Solver

This guide walks through a complete lid-driven cavity run: define the case,
validate it, solve it, inspect the output files, plot the fields, and compare
the centerline velocities with the Re=100 Ghia reference.

The same JSON handoff can be generated by a CFD setup application. The setup
application does not need to import solver code: it writes the versioned case
document, invokes the backend, then reads the returned summary and artifacts.

## 1. Supported Problem Scope

Case schema version `1.0` currently supports:

- 2D incompressible, laminar flow of a constant-property Newtonian fluid in
   either steady-state or transient mode.
- A rectangular domain with a uniform Cartesian mesh.
- Uniform initial `u`, `v`, and pressure values.
- No-slip and tangential moving-wall boundaries with constant velocity or a
   piecewise-linear time/velocity profile.
- Homogeneous Neumann pressure-correction boundaries.
- The M3-M6 transient projection solver and M7 post-processing tools.

This is deliberately narrower than a general CFD setup system. Inlets/outlets,
compressible or turbulent models, spatially varying materials, nonuniform or
unstructured meshes, and additional boundary types are rejected by schema
version 1.0. Extend the schema and adapter with tests before sending those
features from a setup application.

## 2. Install and Run the Complete Example

From the project root, install the package and its test tools:

```powershell
python -m pip install -e ".[test]"
```

Run the dedicated user workflow:

```powershell
python examples/run_user_case.py
```

The default case is
[`cases/lid_driven_cavity_re100_steady.json`](../cases/lid_driven_cavity_re100_steady.json).
It uses fixed pseudo-time increments to reach the configured steady-state
criteria. The reported count is iterations; pseudo-time is not physical elapsed
time. A separate transient example is
[`cases/lid_driven_cavity_re100_transient.json`](../cases/lid_driven_cavity_re100_transient.json),
which ramps the lid from 0 to 4 m/s over four seconds and holds that speed
through its six-second end time.

Run the steady default or select the transient case explicitly:

```powershell
python examples/run_user_case.py
python examples/run_user_case.py --case cases/lid_driven_cavity_re100_transient.json --output results/lid_driven_cavity_transient
```

To run another schema-v1 case and choose an output directory:

```powershell
python examples/run_user_case.py --case path/to/setup-export.json --output results/my_case
```

The command has two visualization modes. The default `save` mode writes the
geometry and final-result PNGs without opening windows. `live` mode opens the
geometry window before the solve, updates speed/pressure/convergence windows
after every time step, and still saves the same PNGs and data files. Select it
with an interactive Matplotlib backend:

```powershell
python examples/run_user_case.py --mode save
python examples/run_user_case.py --mode live
```

The live windows stay open at the final state until closed. `--live` remains a
short alias for `--mode live`. Headless systems should use `save` mode; it
preserves the geometry, final-field, centerline, and convergence PNGs without
requiring a display server.

The command returns exit code `0` for a converged simulation and `2` if the
case reached its maximum step count without converging. In either case, it
writes available fields and diagnostics so a capped run can be inspected.

## 3. Define the Problem

The complete JSON structure is in the example case linked above. Its main
sections are:

| Section | Purpose |
| --- | --- |
| `schema_version`, `case_id` | Contract version and stable setup identifier |
| `units` | Unit system; version 1.0 requires SI |
| `physics` | Incompressible laminar model and `transient` mode selector |
| `domain`, `mesh` | Rectangle dimensions and uniform cell counts |
| `material` | Density and dynamic viscosity |
| `initial_conditions` | Uniform initial velocity and pressure |
| `boundary_conditions` | One supported velocity-wall type per side and pressure-correction condition |
| `solver` | Fixed pseudo-time step or transient time-step cap, CFL limit, step limits, and tolerances |

For example, the Re=100 case uses the following key values:

```json
{
  "domain": {"type": "rectangle", "width_m": 1.0, "height_m": 1.0},
  "mesh": {"type": "uniform_cartesian", "nx": 16, "ny": 16},
  "material": {
    "type": "newtonian_fluid",
    "density_kg_m3": 1.0,
    "dynamic_viscosity_pa_s": 0.01
  },
  "initial_conditions": {"u_m_s": 0.0, "v_m_s": 0.0, "pressure_pa": 0.0},
  "boundary_conditions": {
    "west": {"type": "no_slip_wall"},
    "east": {"type": "no_slip_wall"},
    "south": {"type": "no_slip_wall"},
    "north": {"type": "moving_wall", "velocity_m_s": [1.0, 0.0]},
    "pressure_correction": "homogeneous_neumann"
  }
}
```

The JSON Schema requires all top-level sections and `solver.max_steps`; other
solver controls use defaults. Set `physics.transient` to `false` for steady-state
iteration. In steady mode, the solver selects one conservative fixed pseudo-time
step at startup, capped by `max_time_step_s` if supplied. For finite transients,
include `end_time_s`; the solver uses CFL-limited physical steps and converges
each step before advancing. `max_inner_iterations_per_time_step` bounds that
inner convergence loop. Copy a full case and update the mesh, material, wall
data, and mode-specific solver settings together. For the square cavity,

`Re = density * lid_speed * cavity_width / dynamic_viscosity`.

Thus `rho=1 kg/m^3`, `U=1 m/s`, `L=1 m`, and `mu=0.01 Pa.s` give Re=100.
The solver does not infer a benchmark Reynolds number from a case ID; it uses
the physical values in the document.

## 4. Validate and Run From Python

A setup application can validate its generated mapping before launching the
backend. Schema errors identify the offending JSON path, and unsupported
features are rejected before numerical work begins.

```python
import json
from pathlib import Path

from fvm import PythonFVMBackend, validate_case_document

case_path = Path("cases/lid_driven_cavity_re100_workflow.json")
case_document = json.loads(case_path.read_text(encoding="utf-8"))
validate_case_document(case_document)

run = PythonFVMBackend().run(
    case_document,
    output_directory=Path("results/lid_driven_cavity_re100"),
)
print(run.summary["status"])
print(run.summary["steps"], run.summary["final_time_s"])
```

The file-based variant performs loading and validation for you:

```python
from fvm import PythonFVMBackend

run = PythonFVMBackend().run_file(
    "cases/lid_driven_cavity_re100_workflow.json",
    output_directory="results/lid_driven_cavity_re100",
)
```

`run.simulation` contains the solver-native fields and history. For steady
cases, `final_time_s` is `null` and `final_pseudo_time_s` is reported separately.
For transient cases, `final_time_s` is physical simulation time. `run.summary`
is a JSON-compatible integration result intended for setup software. The
backend is independent of the calling application's classes and APIs.

Applications that need custom per-step visualization can use the observer
instead of the CLI's plotting helper. It is called once after each full
predictor/pressure/projection step and receives read-only-by-contract defensive
copies, so observer code cannot change the run state:

```python
def show_step(diagnostics, velocity, pressure):
   print(
      diagnostics.step,
      diagnostics.time,
      diagnostics.max_divergence_after,
   )

run = PythonFVMBackend().run_file(
   "cases/lid_driven_cavity_re100_workflow.json",
   step_observer=show_step,
)
```

## 5. Check Convergence Before Trusting a Result

Steady cases stop when velocity change, continuity, mass balance, and linear
solver tolerances pass. Transient cases apply the same criteria inside every
physical time step and stop if a step cannot converge within its configured
inner-iteration limit. Inspect the result status and final history entry:

```python
last_step = run.simulation.history[-1]
print("converged:", run.simulation.converged)
print("termination:", run.simulation.termination_reason)
print("max divergence:", last_step.max_divergence_after)
print("global mass imbalance:", last_step.global_mass_imbalance)
print("velocity change:", last_step.velocity_change)
```

In steady mode, the solver selects a fixed pseudo-time step once at startup and
caps it to honor the CFL limit; the chosen step remains constant throughout the
run. In transient mode, `max_time_step_s` is a cap, and each step is reduced as
needed to honor the explicit-convection CFL limit. A `time_step_not_converged` result
means the solver stopped at that physical step; increase
`max_inner_iterations_per_time_step` or adjust tolerances before trusting the
trajectory. `maximum_steps_reached` means the steady run did not converge or a
transient run did not reach `end_time_s`.

## 6. Read the Output Artifacts

The output directory contains:

| File | Contents |
| --- | --- |
| `case.json` | Canonical validated case document consumed by the backend |
| `checkpoints/` | Optional restart files and `latest.json` manifest when checkpointing is enabled |
| `summary.json` | Case ID, schema/backend versions, status, Reynolds number, extrema, and final conservation/residual metrics |
| `fields.npz` | Coordinates, pressure, face-centered `u`/`v`, and cell-centered `u`/`v` arrays |
| `metadata.json` | Mesh, solver settings, temporal mode, convergence state, physical/pseudo-time, and extrema |
| `history.csv` | Per-step time or pseudo-time, CFL, inner-iteration count, velocity change, continuity, mass imbalance, and linear residuals |
| `ghia_re100.json` | Interior-point Ghia profile values, RMS errors, and benchmark eligibility |
| `geometry.png` | Domain outline, uniform mesh, and moving-wall direction |
| `cavity_fields.png` | Final velocity magnitude, pressure, and streamlines |
| `ghia_profiles.png` | Computed centerline profiles against Ghia reference points |
| `convergence_history.png` | Velocity change, divergence, and pressure residual over time |

Open the compressed field arrays with NumPy:

```python
import numpy as np

with np.load("results/lid_driven_cavity_re100/fields.npz") as fields:
    pressure = fields["pressure"]
    u_faces = fields["u_faces"]
    v_faces = fields["v_faces"]
    u_cells = fields["u_cell_centers"]
    v_cells = fields["v_cell_centers"]
```

Pressure is cell-centered with shape `(ny, nx)`. Face velocities have shapes
`u=(ny, nx+1)` and `v=(ny+1, nx)`. Cell-centered velocity arrays in the export
are interpolated for plotting and do not replace the staggered solution fields.

## 7. Save and Resume Checkpoints

Checkpointing is optional and separate from result export. The case JSON is the
problem definition; a checkpoint is the solver state needed to continue that
case. `fields.npz`, `metadata.json`, and `history.csv` are post-processing
outputs and are not restart inputs. Checkpoint cadence, retention, and restart
selection are runtime options (`--checkpoint-every`, `--retain-checkpoints`,
and `--restart`); the version 1.0 case schema remains unchanged.

Start a run with a checkpoint every 100 completed steps:

```powershell
python examples/run_user_case.py `
   --case cases/lid_driven_cavity_re100_transient.json `
   --output results/cavity_restart `
   --checkpoint-every 100 `
   --retain-checkpoints 5
```

The output workspace contains:

| File | Purpose |
| --- | --- |
| `case.json` | Canonical copy of the validated case used for this run; also readable as a case input |
| `checkpoints/checkpoint_00000100.npz` | Compressed pressure, staggered velocity, saved case configuration, time/step state, and complete diagnostics history |
| `checkpoints/latest.json` | Atomic pointer to the most recently committed checkpoint, including its SHA-256 digest |
| `fields.npz`, `metadata.json`, `history.csv` | Final result and monitoring exports; useful for analysis, but not sufficient to resume |

The solver writes periodic checkpoints only at complete step boundaries. It
also writes the final safe state on normal completion. A failed finite-transient
inner solve is not treated as a completed physical step, so it does not replace
the last safe checkpoint. If the process is forcibly terminated, recovery starts
from the latest committed checkpoint and may repeat work since that checkpoint.
An incomplete write cannot replace the previous `latest.json` target.

Resume from the latest checkpoint in the same workspace:

```powershell
python examples/run_user_case.py `
   --case results/cavity_restart/case.json `
   --output results/cavity_restart `
   --checkpoint-every 100 `
   --restart latest
```

To resume a particular checkpoint instead, pass its filename:

```powershell
python examples/run_user_case.py `
   --case results/cavity_restart/case.json `
   --output results/cavity_restart `
   --checkpoint-every 100 `
   --restart checkpoint_00000100.npz
```

`--restart` requires `--checkpoint-every`, so the continued run keeps producing
recovery points. `--retain-checkpoints` defaults to 5; older files are removed
only after a newer checkpoint and its manifest have been committed.

On restart, the mesh, material, boundary conditions, initial case definition,
and numerical controls must match the saved case. You may increase `solver.max_steps`
and, for a finite transient, increase `solver.end_time_s`; reducing either is
rejected. For example, copy the case to a new JSON file, increase the applicable
run limit, then pass that file with `--case`. `max_steps` is the total global
step limit, not an additional-step count: to continue checkpoint step 1,000 to
step 2,000, set `max_steps` to 2,000. All other case fields must remain
unchanged. Checkpoints include the configuration that produced them, so the
case file can be validated before any solver step is advanced.

The same workflow is available through the Python backend:

```python
from fvm import PythonFVMBackend

backend = PythonFVMBackend()
first_run = backend.run_file(
      "cases/lid_driven_cavity_re100_transient.json",
      output_directory="results/cavity_restart",
      checkpoint_every=100,
)

continued_run = backend.run_file(
      "results/cavity_restart/case.json",
      output_directory="results/cavity_restart",
      checkpoint_every=100,
      restart="latest",
)
```

This example resumes an interrupted run with its original limits. To continue
after a configured step or end-time limit, pass a copied case with the relevant
limit increased as described above; do not change its other fields.

For a selected file, use `restart="checkpoint_00000100.npz"`. The backend also
accepts an absolute checkpoint path. The Python API and CLI use the same
checkpoint directory and file format.

## 8. Interpret the Ghia Comparison and Visuals

The workflow interpolates the staggered velocities onto `x=0.5` and `y=0.5`,
then computes RMS errors at Ghia's interior Re=100 sample coordinates. Wall
endpoints are excluded, including the discontinuous moving-lid corners. The
reference data source and DOI are documented in
[`src/fvm/postprocessing.py`](../src/fvm/postprocessing.py).

`ghia_re100.json` includes `benchmark_valid`. It is true only when the
simulation reports convergence and the run matches the square Re=100 benchmark
assumptions. A short, capped run can still produce plots and RMS values for
diagnosis, but those numbers are not a benchmark pass. The 16 by 16 example is
for learning the workflow; use the optional grid-study API and compare
successively refined, converged runs before making grid-independence claims.

The live plot updates on every solver step when `--live` is enabled. Saved PNGs
show the starting geometry and final state. The PNGs can also be regenerated/customized through
`plot_cavity_fields`, `plot_ghia_comparison`, and
`plot_convergence_history` in `fvm.postprocessing`.

## 9. Adapt This Workflow

For another problem supported by schema version 1.0:

1. Copy the case JSON and assign a unique `case_id`.
2. Set rectangle dimensions, uniform mesh counts, fluid properties, and
   initial fields in SI units.
3. Assign one supported wall condition to each side. Moving-wall velocity
   must be tangential to its side.
4. Choose steady fixed pseudo-time or transient physical-time controls. For a
   transient, define `end_time_s` and optionally a tabulated wall velocity
   profile; its points must have increasing `time_s` values and tangential
   velocity components.
5. Validate the document, run it through `PythonFVMBackend`, and inspect the
   convergence status before comparing results.
6. Use the exported fields and diagnostics or add problem-specific post-
   processing around `run.simulation`.

For capabilities outside that list, extend the versioned schema and adapter
with focused tests and documentation rather than encoding extra meanings in
existing fields. This keeps the setup-software interface explicit and lets
both projects evolve independently.

## 10. Compare Data Externalization Strategies

For a plain-language explanation of the strategies and a step-by-step user
comparison guide, see
[`data_externalization_guide.md`](./data_externalization_guide.md).

The solver's numerical loop remains responsible only for solving. The existing
completed-step observer is the boundary to a separate `fvm.externalization`
package: it captures an immutable, versioned `StepSnapshot` and passes it to a
selected transport. Snapshots contain mesh coordinates, pressure, staggered
velocities, and step diagnostics. They are compressed NumPy archives written
without pickle; the common `SnapshotStore` commits each file atomically. A
consumer or visualization tool can read the snapshots without importing solver
classes. The store partitions files under validated run-ID directories, so
independent runs do not collide on step numbers.

The included local strategies are:

| Strategy | Data path | Solver-side cost | Useful when |
| --- | --- | --- | --- |
| `sync` | Write each snapshot directly to the result store | Includes full file serialization and write time | Small cases, simplest reliable local export |
| `shared` | Write an atomic snapshot to a shared-folder spool; a separate poller copies it on its schedule | Spool write only; the poller's processing is decoupled | Larger runs or a separately deployed externalizer |
| `async` | Enqueue into a bounded in-process queue; a worker writes snapshots | Queue handoff until the bounded queue fills; close drains the queue | Local runs where some storage latency can be overlapped |
| `grpc` | Bounded client queue and streaming gRPC to a snapshot service | Queue handoff plus any backpressure from the bounded stream | A service boundary that can later move to another host |

These are delivery paths, not a promise of zero solver overhead. Shared-folder
and gRPC producers still serialize snapshots and enqueue/write them locally.
The async and gRPC queues are bounded and apply backpressure rather than
silently dropping snapshots. Background write/transport failures are surfaced
when publishing or closing. The shared-folder spool retains source files for
replay; monitor and manage its disk use separately from the solver output.

Install the package (gRPC dependencies are part of the project install), then
run all four strategies against the same case:

```powershell
python examples/compare_externalization_strategies.py --steps 4
python examples/compare_externalization_strategies.py `
  --case cases/lid_driven_cavity_re100_transient.json `
  --strategy grpc `
  --steps 20 `
  --snapshot-every 1
```

The default POC caps each run to four steps so it completes quickly; set
`--steps` to compare longer runs. By default snapshots are externalized every
10 completed steps, with the final step always included; use
`--snapshot-every 1` to publish every step. Each strategy writes its snapshots
and a `final_snapshot.png` under
`results/externalization_poc/<strategy>/<run-id>/`. Each run store contains
atomic `latest.json` pointers beside its step archives. The
`benchmark.csv` and `benchmark.json` report solver wall time, total time
(including drain/close), producer publish time, downstream externalization
time, bytes, completed steps, snapshot interval/count, and wall time per
solver step. This is a local measurement, not a cloud performance claim: run
multiple repetitions on the same host and compare
the same case, mesh, step budget, and filesystem before presenting conclusions.
With the default four-step cap, only the final snapshot is saved because the
run does not reach step 10.

The shared-folder consumer is independently runnable:

```powershell
python examples/poll_shared_snapshots.py `
  --shared results/my_run/shared `
  --destination results/my_run/snapshots `
  --interval 1
```

Wire a strategy to the existing backend without changing the solver itself:

```python
from fvm import PythonFVMBackend
from fvm.externalization import (
    SharedFolderExternalizer,
    create_step_observer,
)

externalizer = SharedFolderExternalizer("results/my_run/shared")
observer = create_step_observer(
    externalizer, "my-run", snapshot_every=10
)
try:
    run = PythonFVMBackend().run_file(
        "cases/lid_driven_cavity_re100_workflow.json",
        step_observer=observer,
    )
    if run.simulation.history:
        observer.publish_final_step(
            run.simulation.history[-1],
            run.simulation.velocity,
            run.simulation.pressure,
        )
finally:
    externalizer.close()
```

`snapshot_every` defaults to 10. The observer publishes steps divisible by
that interval; call `publish_final_step` after the run to make sure the final
state is stored even when it falls between intervals. Set `snapshot_every=1`
to publish every step.

The other strategies implement the same `publish(snapshot)` / `close()`
contract. `GrpcSnapshotServer` is a local demonstration service; it uses
insecure transport on loopback by default. The server's `start(credentials=...)`
and client's `GrpcExternalizer(credentials=...)` accept gRPC TLS credentials.
The client stream has no deadline by default, so long solves are not cut off
while snapshots are being published; set `timeout_seconds` when a bounded
stream lifetime is required.
Before deploying across a network, configure authentication/authorization,
resource limits, retry/idempotency policy, and a durable cloud-backed
`SnapshotStore`. The gRPC wire contract is defined in
[`src/fvm/externalization/snapshot_service.proto`](../src/fvm/externalization/snapshot_service.proto).
Snapshot files are stored under `<store>/<run_id>/step_<number>.npz`, with an
atomic `latest.json` pointer per run.

Visualization can consume a snapshot directory independently of solver state:

```python
from fvm.externalization import SnapshotStore, plot_latest_snapshot

plot_latest_snapshot(
    SnapshotStore("results/my_run/snapshots"),
    "results/my_run/latest.png",
)
```

Implement a new transport by satisfying the small `Externalizer` protocol and
keeping the existing `StepSnapshot` schema stable. This keeps solver
responsibility, transport implementation, storage, and visualization
separately replaceable.

### Run a case and plot each externalized step

Use the separate example when you want to run your case with one strategy and
create plots from the saved snapshots:

```powershell
python examples/run_externalized_case.py `
  --case path/to/your-case.json `
  --strategy async
```

Choose `sync`, `shared`, `async`, or `grpc` with `--strategy`. The default is
`sync`. By default it externalizes every 10 solver steps plus the final step;
set `--snapshot-every 1` for every step. The script saves one PNG per
externalized snapshot under
`results/externalized_case/<strategy>/<run-id>/step_plots/` and a
`final_result.png` beside that folder. Each plot is loaded from the selected
strategy's externalized snapshot store, not from the solver's in-memory result.
For a shorter demonstration without editing the case, add `--max-steps 4`.
The case's configured step limit is used when that option is omitted.

Add `--mode live` to display snapshots as they become available in that store:

```powershell
python examples/run_externalized_case.py `
  --case path/to/your-case.json `
  --strategy async `
  --mode live
```

Live mode needs an interactive Matplotlib backend. The solver runs in the
background while the viewer reads committed snapshots from the store; it does
not plot from the solver callback. It keeps one plotter window open, updates the
field panels in place, and appends each step to the convergence history. The
`shared` view can therefore lag by the polling interval. The final plot stays
open until you close it, after which the per-step PNGs and `final_result.png`
are saved.
